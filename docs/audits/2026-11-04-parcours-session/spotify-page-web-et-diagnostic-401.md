# Page Web Spotify séparée et diagnostic du 401

## Livraison et périmètre

APK expérimental construit depuis `fcddd282cfa06de38fbdd70b382dfb2e1df790eb`, package `com.melodix.music.preview`, versionCode `1023015` : [ZIP contenant l'APK](https://github.com/Souxch06/Melodix/actions/runs/43387229949/artifacts/14018234772). Le visuel de l'accueil Glass n'a pas été refait ; un bouton réutilisant le style existant ouvre une activité distincte, titrée « Spotify (page Web) », avec un retour vers Melodix. Ce n'est pas la réparation de l'accueil natif.

La nouvelle WebView charge la page officielle, sans interface JavaScript Melodix, sans injection de script, sans extraction, export, journalisation ni copie par ce nouveau code de contenu de page, de jeton ou de cookie. Elle ne renseigne pas le gate ni la preuve de bibliothèque. La navigation principale est limitée à HTTPS sur les deux hôtes exacts `open.spotify.com` et `accounts.spotify.com` ; une connexion passant par un fournisseur tiers pourrait être bloquée. L'activité n'est pas exportée et son bouton Retour la ferme. La WebView utilise le profil Android existant pour la session, JavaScript et DOM storage sont activés pour la page Spotify ; son stockage Web habituel peut donc persister des données de site. Le mode cache exige le réseau mais **ne garantit pas l'absence de toute écriture du moteur WebView**. Aucune suppression de données ni copie de session entre profils n'est réalisée. Il ne faut pas interpréter ces propriétés comme une navigation privée/incognito ou une garantie que Spotify ne conserve aucune donnée de site.

## Ce qui est établi dans les sources et observations

1. La capture fournie montre que le lecteur Web Spotify affiche du contenu personnalisé. Elle ne prouve ni que l'appel distinct `libraryV3` a été autorisé, ni qu'un élément précis est une playlist privée récupérée par Melodix.
2. La version historique `81b30f4`, dans `scripts/spotify_bridge.source.js::fetchWebPlayerToken`, effectuait un GET credentialed à l'endpoint de jeton du lecteur, puis un GET de repli. Les requêtes ont des en-têtes d'identification de plateforme ; elles ne constituent pas un échange OAuth PKCE et ne fournissent **ni grant type, ni redirect URI, ni code verifier, ni scopes explicites**. Le code ne vérifiait pas les scopes d'un éventuel jeton obtenu ; les scopes effectivement attachés sont **non établis**. Aucun contenu de jeton n'est nécessaire à ce constat.
3. Dans `81b30f4`, en cas de succès et de validité temporelle, le code gardait temporairement un jeton du lecteur et l'ajoutait comme Bearer à la requête `libraryV3`. Si les deux endpoints renvoyaient les refus indiqués pour **une même tentative sans cache utilisable**, aucun jeton n'était obtenu et ce code arrêtait la requête bibliothèque avant son envoi. Les observations 400 JSON catégorie `auth`, puis 403 HTML marqueur `access_denied`, ne révèlent pas pourquoi les endpoints ont refusé ni quels scopes auraient été accordés. Une corrélation d'une tentative précise est indispensable avant d'affirmer que ces refus et un éventuel 401 proviennent du même flux.
4. Le code actuel, après retrait de l'acquisition de jeton privé, n'envoie **aucun Bearer** à `libraryV3`. Il utilise une requête WebView `credentials: include` (transmission éventuelle des cookies par le navigateur selon ses règles), sans paramètre de scopes, et ne lit ni ne copie ces cookies pour former la requête. Les scopes associés à la session Web sont **non établis**. La présence effective de cookies sur le réseau ne peut pas être déduite de `credentials: include` seul. Le 401 observé sur l'APK ultérieur a été consigné dans `retour-connexion-diagnostic-reel.md` ; il ne doit pas être fusionné avec les refus de jeton de la version historique.
5. Le code actuel invalide la preuve et les données privées natives sur un 401 ou 403 ; aucun de ces codes ne valide une session. `NativeSessionGate` n'accepte une bibliothèque que sur une réponse réussie et validée. Les getters de génération étaient OK dans les observations transmises, sans prouver le fonctionnement de la bibliothèque.

## Non établi et prochaine mesure

La cause exacte du 400, du 403 et du 401 est **non établie** : une autorisation absente est compatible avec le 401 actuel, mais les journaux ne démontrent pas si Spotify attend un autre mode d'authentification, refuse la session pour une autre raison, ou si un autre paramètre est en cause. Il n'est pas établi que la remise d'un jeton privé résoudrait le problème ; elle n'est pas réalisée.

Sur le téléphone, vérifier d'abord le bouton « Spotify (page Web) », le titre, le retour, les interactions et la visibilité du contenu dans cette page, sans envoyer de capture contenant des informations privées. Tester ensuite, séparément, « Réessayer la bibliothèque » et relever uniquement le numéro de build, la génération, le nombre d'appels et les codes HTTP/catégories déjà assainis. Ne relever ni corps brut, ni URL complète avec paramètres, ni en-têtes d'autorisation, ni valeur ou liste de cookies/jetons. La présence éventuelle d'une autorisation sur le réseau et son périmètre ne peuvent être tranchés à partir des journaux actuels ; si nécessaire, il faudrait une instrumentation de transport limitée à des indicateurs booléens et catégories sans valeurs sensibles, et un protocole contrôlé sur un compte autorisé. Une observation du DOM ou de la page ne doit pas être promue en preuve de bibliothèque.
