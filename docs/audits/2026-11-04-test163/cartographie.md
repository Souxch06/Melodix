# TEST163 — cartographie avant modification de production

HEAD examiné : `9dd19c6d7aee4f7e1eca299e436eb7ee03b4c8da`, clone isolé propre, branche de la PR #8. Le rapport TEST162 documente déjà les références et les observations Android ; ceci complète la cartographie demandée avant correction.

| Fonction / garde réel | Condition et effet actuels | Comportement cible sans supprimer la protection privée |
|---|---|---|
| `res/layout/activity_main.xml`, `MainActivity.onCreate` | `nativeRoot` est gonflé avec le content view, mais initialement `gone`; un échec de gonflage mène à une vue d'erreur. `NativeSessionGate.bind` est appelé juste après. | Garder le vrai layout et le rendre accessible seulement une fois l'invalidation du contenu antérieur achevée. |
| `NativeSessionSurface.protectUnderlyingViews/paint` | `state != 3` masque le root, retire son accessibilité, puis place une surface de session plein écran ; en login actif, une surface/header laisse la WebView visible. `state == 3` retire l'overlay. | Séparer le shell et le statut de session ; ne pas révéler les vues privées périmées, ni couvrir toute la navigation inutilement. |
| `NativeSessionGate.blocked` appelé par `showNativeUiFrom`, `activateNativeUiRoute`, `applyNativeUiData`, `renderNativeRows` | Tant que `state != 3`, retourne vrai et parfois réaffiche le login. Les deux premières méthodes bloquent l'affichage/les routes ; les deux dernières bloquent des charges de données potentiellement privées. | Autoriser seulement une structure et des états neutres natifs ; conserver un contrôle strict distinct au passage des charges privées et des callbacks. |
| `MainActivity.setNativeScreen`, `showNativeUiFrom`, `activateNativeUiRoute`, `renderNativeRows` | Gardes supplémentaires basés sur `AppSingleton.B`, URL et route de login ; certains déclenchent `applyLoginWebUi/revealLoginWebUi`. | Ne pas confondre route de session et autorisation des données ; aucune donnée non prouvée ne doit passer. |
| `MainActivity.handleNativeSystemBack` | `state != 3` termine l'activité ; sinon gère les routes natives. | Retourner dans le shell ou fermer explicitement la connexion sans restaurer une charge privée. |
| `NativeSessionGate.initialUrl`, `pageFinished`, `begin`, `result`, `resume`, `destroy`, `webFailure` | États 0 vérification, 1 sans session, 2 expirée, 3 valide, 4 erreur ; absence de cookie déclenche automatiquement `accounts.spotify.com`, et seul token + réponse bibliothèque 2xx permettent 3. Reprise depuis 3 relance une vérification ; rotation et activité finale ont des traitements différents. | Garder les preuves distinctes des vues ; toute perte ou revalidation doit neutraliser les données avant affichage. |
| `MainActivity.A` / `NativeLogoutRunnable`; `NativeSessionReconnect.start` | Déconnexion explicite utilise la routine historique ; la reconnexion explicite confirmée efface les données WebView. La vérification ordinaire conserve les cookies. | Neutraliser affichage/charges lors de l'invalidation, sans effacer préférences ou cookies sur simple erreur. |
| `NativeUiUpdateRunnable`, `MainActivity.postNativeUiData/applyNativeUiData` | Callback en file avec écran et payload sans époque propre ; `applyNativeUiData` et `renderNativeRows` sont gardés aujourd'hui. | Invalider les charges en vol avant d'ouvrir le shell ; le contrôle de provenance doit aussi couvrir l'émission JS, pas seulement la file native. |
| `scripts/spotify_bridge.source.js` | `mediaLib`, preuve/époque d'auth, promesses et contrôleurs sont invalidés par `invalidateLibraryProofForAuthChange` lors de changements de signaux ; certaines erreurs non-401/403 conservent de précédentes données pour réessai. | Empêcher toute réutilisation/émission tant que l'identité n'est pas revalidée ; ne pas modifier les cookies ni les préférences non privées. |
| `MainActivity` stockage d'écran | `nativeCurrentJson/Title`, `nativeReturnJson/Title/ExpectedId/Search`, `nativeExpectedId/Search`, `nativeCurrentScreen` et drapeaux Home/lecteur peuvent survivre aux transitions ; `onNativeBackClick` restaure des données du retour. | Nettoyer les références privées et reconstruire un état neutre avant de révéler la navigation ; invalider génération réglages et réponses en vol. |
| `nativeContent`, profil, mini/full player | Le contenu natif réutilise un `LinearLayout`; titres, artistes, images et `nativeHasTrack` restent dans les vues. `NativeImageLoader.load` utilise Picasso et annule une requête quand on le recharge ; les caches d'images réseau restent distincts des réglages. | Détacher les anciennes lignes et annuler les chargements des images encore visibles ; vider les titres/illustrations et cacher le lecteur périmé. |
| `c91.onPageFinished`, `NativeBridgeNavigation.prepare` | Chargement/injection des assets sur le chemin WebView player ; AndBridge autorisé uniquement HTTPS `open.spotify.com` port défaut/443, absent sur accounts/tiers. La fixture TEST161 injecte manuellement et ne démontre pas le bootstrap produit. | Conserver strictement l'origine ; séparer la validation d'injection automatique de toute fixture et de l'authentification réelle. |

Le layout démo utilise des identifiants proches mais est une activité distincte. Les captures de démo ne démontrent pas le shell. Le nettoyage doit se produire sur le thread UI et précéder toute exposition du root ; la gestion des retours tardifs et des images est nécessaire pour éviter un simple masquage temporaire. Les API Spotify internes ne sont pas l'API OAuth officielle et leur échec n'identifie pas nécessairement une expiration.
